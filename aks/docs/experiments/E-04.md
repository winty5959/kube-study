## Purpose and expected behavior

Replace the API image with a previously published version and restore the current
version. With `maxUnavailable=0` and two Ready replicas, Traefik must continue
serving requests while old and new API Pods overlap.

## Preconditions

The API HPA minimum and maximum were temporarily set to two replicas. Both
replicas were Ready; the API PDB allowed one disruption. Automated sync was
paused on `root-dev` and `album-dev` so Argo could not replace the deliberate
live image change before observation. The image digest for the previous tag was
verified from the GHCR manifest before rollout.

## Procedure and observations

The request observer ran for 45 seconds through a port-forward to the stable
Traefik service and sent the `album.aks.localhost` host header. The API image
changed from `sha-b7122b7` to `sha-4486b3b`, then back to `sha-b7122b7`.
Both Deployment rollouts completed successfully.

The observer recorded 162 requests, all HTTP 200: 128 from `sha-b7122b7` and
34 from `sha-4486b3b`. It saw six serving Pod identities across the two
rollouts. Latency ranged from 16.6 ms to 92.5 ms, with 22.8 ms average. The
request log was summarized locally and not added to the repository.

## Recovery

The current Git image tag `sha-b7122b7` was restored and its rollout completed
with two Ready replicas. The HPA minimum returned to one. `root-dev` and
`album-dev` were restored to automated sync and returned Synced/Healthy. The
Deployment may remain at two replicas for its normal HPA scale-down stabilization
interval; the declared minimum and image tag are back at their original values.

## Limits

This covers short photo-list GET requests and one API image version change in
the two-node dev cluster. It does not measure upload behavior, streaming
connections, or availability during node failure.
