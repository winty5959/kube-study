## Purpose and expected behavior

Cause a single generated image to exceed a deliberately reduced worker memory
limit. Kubernetes should report `OOMKilled`; the retry limit should eventually
mark the photo `FAILED` rather than retrying forever.

## Preconditions

Both Redis lists were empty. `root-dev` and `album-dev` automated sync were paused.
KEDA was paused at one worker replica. The worker started with its normal
128Mi request and 512Mi limit; the experiment temporarily reduced these to
32Mi and 64Mi.

## Procedure and observations

One generated 9000×9000 PNG, 258,637 bytes, was uploaded through the API. The
upload was accepted. The worker Pod restarted three times; its last terminated
container reason was `OOMKilled` with exit code 137 under the 64Mi memory limit.
After three processing attempts, the isolated photo reached `FAILED` and the
status script reported one FAILED fixture.

## Recovery

The test fixture was deleted by its generated ID. Both `thumbnail:jobs` and
`thumbnail:processing` were empty. The worker memory request/limit returned to
128Mi/512Mi, the KEDA pause annotation was removed, and the worker returned to
zero replicas. `root-dev` and `album-dev` automated sync were restored and both
Applications were Synced/Healthy. The API, frontend, Postgres, Redis, MinIO,
and their PVCs were not changed by this experiment.

## Limits

This proves isolation and bounded retry for one generated image at the tested
64Mi limit. It does not imply that all image sizes succeed at the normal limit,
or that a deleted worker Pod preserves in-memory state without the durable queue.
