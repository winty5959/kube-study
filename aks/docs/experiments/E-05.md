## Purpose and expected behavior

Temporarily make new API Pods fail readiness. With two previous Pods Ready,
`maxUnavailable=0`, and `maxSurge=1`, the Deployment should stop the rollout
after its progress deadline and preserve the existing service.

## Preconditions

Two API Pods were Ready; PDB reported two healthy Pods and one allowed disruption.
Automated sync was paused on `root-dev` and `album-dev`. The API HPA minimum was
temporarily set to two so the previous replicas could not scale down.

## Procedure and observations

Through the Traefik port-forward, a continuously running observer queried the
read-only API list route. The API `readinessProbe.httpGet.path` was changed from
`/readyz` to `/intentionally-not-ready`, and `progressDeadlineSeconds` was
temporarily reduced from 180 to 60.

The Deployment reported `ProgressDeadlineExceeded`. The new ReplicaSet had one
desired Pod and zero Ready; the existing ReplicaSet retained two desired and two
Ready Pods. The Deployment still reported two Ready replicas. During the 85-second
observation, 306 requests all returned HTTP 200 from the existing `sha-b7122b7`
Pods. No new invalid Pod became a service endpoint.

## Recovery

The readiness path was restored to `/readyz` and the deadline to 180 seconds.
The rollout completed with API image `sha-b7122b7` and two Ready replicas. HPA
minimum was restored to one. `root-dev` and `album-dev` were returned to automated
sync; the child was Synced/Healthy and its readiness and image matched Git. The
root Application initially retained a failed operation from the paused child;
a manual root sync reapplied the declared child policy, after which root-dev was
Synced/Healthy with no pending operation. The HPA was still at two replicas at
observation time due its scale-down stabilization; no replica or HPA manifest
change remains.

## Limits

This tests a readiness failure during an API rollout in dev. It does not test
application startup failure, database unavailability, or node-level failure.
