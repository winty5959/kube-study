## Purpose and expected behavior

Check the application data NetworkPolicies directly: frontend Pods must not
connect to PostgreSQL, while API Pods must be able to connect on TCP 5432.

## Preconditions

`album-dev` was Synced/Healthy with automated sync enabled. PostgreSQL was
Ready. The `default-deny`, `application-data-egress`, and `data-ingress`
NetworkPolicies were present.

## Procedure and observations

The current PostgreSQL Pod endpoint was read from the `postgres` Service. From
a frontend Pod, BusyBox `nc -zvw 2 <postgres-pod-ip> 5432` timed out. From an
API Pod, Python `socket.create_connection(("<postgres-pod-ip>", 5432), timeout=3)`
connected to that same endpoint. Using the same endpoint removed DNS behavior
from the policy comparison.

| Time KST | Observation | Evidence |
|---|---|---|
| 02:36 (approx.) | Frontend to the PostgreSQL Pod endpoint on TCP 5432 timed out | `kubectl exec <frontend-pod> -- sh -c 'busybox nc -zvw 2 <postgres-pod-ip> 5432'` returned `Operation timed out` |
| 02:36 (approx.) | API to the same PostgreSQL Pod endpoint on TCP 5432 connected | `kubectl exec <api-pod> -- python -c 'socket.create_connection(("<postgres-pod-ip>",5432),timeout=3)'` |

## Recovery

The experiment made no NetworkPolicy changes, so there was no temporary allow
rule to remove. PostgreSQL, the API, and both frontend replicas remained
Ready. `root-dev` and `album-dev` remained Synced/Healthy with automated sync
enabled.

## Limits

This verifies the existing frontend/API to PostgreSQL policy paths. It does
not test every application egress destination or external network route.
