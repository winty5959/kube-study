## Run

The baseline `album-prod` API had two Ready replicas on the `aks-v1.0.1` declaration. The prod
photo table contained zero rows and the Redis job lists were empty. The previous Deployment
revision was available in rollout history.

Ran a live Deployment rollback:

```sh
kubectl rollout undo deployment/api -n album-prod --to-revision=1
```

The Deployment rolled to the `aks-v1.0.0` image reference with two Ready replicas. Argo CD
reported `album-prod` as `OutOfSync` and `Healthy`; automated sync was still disabled. This
demonstrated that a live rollback does not change the Git release declaration.

Manually syncing `album-prod` at main revision `1b7e521becccb6117d578d3a1f06132684631f5a`
restored the `aks-v1.0.1` image reference. The PreSync migration completed, the PostSync smoke
Job succeeded, and the Application returned `Synced` / `Healthy` with a successful operation at
2026-10-18 17:26:08 UTC. A first retry during API pod replacement stopped at the HPA health gate;
the next sync ran after HPA metrics were valid. No automatic prod reconciliation occurred.

## Recovery and limits

The Git declaration on `main` remained at `aks-v1.0.1` for the entire experiment, so no Git revert
commit was needed. Manual Argo sync restored that existing declaration after the live rollback.
This run proves drift detection and manual Git reconciliation; it does not test rollback to a
different Git commit or behavioral differences between the two API aliases. No prod user data,
PVC, Azure resource, or K3S resource was changed or deleted.
