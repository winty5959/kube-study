## Purpose and expected behavior

Generate read-only API load and observe HPA scaling from one to multiple API
replicas and back to one after load. This checks the configured CPU target; it
is not a throughput commitment.

## Preconditions

Metrics Server was Available. The API HPA targeted 60% of CPU requests, allowed
one to three replicas, and used the configured 300-second scale-down stabilization.
The successful transition run started with one API replica. A previous harness
attempt began from an already scaled HPA and its direct port-forward ended early;
its connection failures were excluded and the run was repeated after the HPA
returned to one replica.

## Procedure and observations

The passing three-minute run used 200 virtual users against read-only photo-list
requests. It completed 143,495 requests/checks with 100% checks, zero failed
checks, zero HTTP errors, and 652.24 average requests per second. The API HPA
reached two replicas at 00:59:17 KST, three at 01:00:17, and returned to one at
01:09:01 after the scale-down stabilization interval.

A separate 200-VU run while the API already had three replicas completed 148,576
requests with zero HTTP errors. It is recorded separately and does not count as
the 1→N→1 transition run.

## Recovery

The read-only load stopped. The API returned to one replica, worker replicas
returned to zero, and the normal HPA min/max policy remained in Git. No photo rows
or objects were created or changed. The failed tunnel attempt is retained as a
test-harness limitation in [A10 evidence](../../../.omo/evidence/aks-implementation/A10-observability.txt).

## Limits

The request mix was read-only and the 200 virtual users do not represent a
production arrival pattern. A live CPU sample reached 85% on one node; that
concentration and the two-node size are recorded in the linked A10 evidence.
